# v0.5 — Sliding-causal under DualChunkSwap

**Status**: design only (2026-04-29). v0 ships without sliding-causal
(SPEC §2 explicitly drops it). This doc captures the approach so the
implementation can pick it up later without rediscovering the problem.

**Pre-reads**: `docs/cp/SPEC.md` (v0 contract; §2 deployment quirks
and the "What v0 does NOT support" table), `docs/cp/hstu_cp_design.md`
§3 / §4 (DualChunkSwap chunk layout, three-region tile classification).

---

## 1. The problem

The HSTU CUTLASS kernel takes a single `window_size = (w_left,
w_right)` tuple and applies it against **local** Q/K positions. After
DualChunkSwap chunking, "local" positions on a rank no longer
correspond to "global" positions in the original sequence, so a naive
per-tile `window_size=(w, 0)` kernel call does **not** reproduce the
global sliding window.

Concrete example (`cp_size=4`, sample length `L=8`, chunk size `c=L/(2·cp)=1`).
Global chunks are indexed 0..7 in time order. DualChunkSwap places
chunks `{r, 2·cp-1-r}` on rank `r`:

| rank | chunks held (global indices) | local layout |
| ---- | ---- | ---- |
| 0    | {0, 7}                       | `[g0, g7]`  |
| 1    | {1, 6}                       | `[g1, g6]`  |
| 2    | {2, 5}                       | `[g2, g5]`  |
| 3    | {3, 4}                       | `[g3, g4]`  |

For sliding-causal with `w=2` (each token attends to up to 2 past
global tokens, including itself), the global window for `g7` is
`{g5, g6, g7}`. On rank 0, `g7` lives at local position 1; the K
positions reachable along the ring during the (rank, step) grid are:

| step | rank-0 sees peer's KV from | global chunks | g7 needs from this set |
| ---- | -- | -- | -- |
| 0    | rank 0 (self)            | {g0, g7}     | {g7}                |
| 1    | rank 3 (lower-tri)       | {g3, g4}     | ∅                   |
| 2    | rank 2 (upper-tri)       | {g2, g5}     | {g5}                |
| 3    | rank 1 (upper-tri)       | {g1, g6}     | {g6}                |

So the global window for `g7` straddles **three** ring steps and
matches keys at non-contiguous local-K positions in each step. The
kernel's single `window_size` argument cannot express this directly.

## 2. Design options

### 2.A — Per-tile mask remap (heavy)

For each tile (rank, step), compute the local-K → global-K position
map and pass an explicit row-position vector to the kernel so it can
apply `(local_q_pos, global_k_pos)` window logic per cell.

**Pros**: bit-exact match against the single-GPU baseline.
**Cons**:
1. Requires a kernel signature change (`hstu_attn_varlen_func` does
   not currently accept a per-row K-position vector).
2. The CUTLASS template would need to be re-instantiated; we are
   downstream consumers of the FBGEMM-style installed kernel and do
   not control its source. Out of scope for v0.5.

**Verdict**: not the path. Block on FBGEMM upstream change.

### 2.B — Per-tile in-/out-of-window classification (recommended)

For each tile, classify whether **any** Q-K pair in this tile can
land inside the global sliding window. Three outcomes:

1. **No overlap**: the global K positions held by this tile are all
   outside the global `[Q_global_pos - w, Q_global_pos]` window for
   every Q in the tile. Skip the kernel call entirely; tile contributes
   0 to the partial sum.
2. **Full overlap**: every Q-K pair in the tile lies within the global
   window. Run the kernel with `window_size=(-1, 0)` (pure causal) for
   diag/lower tiles, or `window_size=(-1, -1)` (no mask) for upper
   tiles — same as v0 today.
3. **Boundary tile**: some Q-K pairs are in window, some are not. Run
   with the v0 mask first, then mask out the out-of-window cells via
   a post-pass scatter that zeros the affected rows of the partial
   output. The mask geometry depends on `(cp_rank, step, w)` and is
   computable from the chunk indices held by source/dest ranks.

**Pros**: no kernel signature change. Reuses the v0 wrapper machinery.
Most tiles classify as "no overlap" or "full overlap" when `w` is
small, so the boundary work is small.

**Cons**: boundary tiles need a per-row mask post-pass, adding an
extra Python-side scatter. For `w << L`, fraction of boundary tiles
is `O(w/c)` where `c=L/(2·cp)` so the cost scales with `w`, not with
the full ring.

**Verdict**: this is the path for v0.5.

#### 2.B mechanics

For each Q-chunk × K-chunk pair we compute the **min** and **max**
global token-gap across all (q_pos, k_pos) cells in that chunk-pair
sub-tile. Let `c = L / (2·cp_size)` be the chunk size and let
`g_q`, `g_k` be the global chunk indices of the Q and K chunk
respectively. Token positions inside chunk `g` span global indices
`[g·c, (g+1)·c)`. For pure-causal sliding window `(w, 0)`:

```
  gap(q_pos, k_pos) = q_pos - k_pos  (positive ⇒ k is in the past)
  min_gap = (g_q · c)         - ((g_k + 1) · c - 1)
          = (g_q - g_k - 1) · c + 1
  max_gap = ((g_q + 1) · c - 1) - (g_k · c)
          = (g_q - g_k + 1) · c - 1
```

A chunk-pair sub-tile classifies as:

- **No overlap (skip)**: `min_gap > w` (every k is too far in past)
  *or* `max_gap < 0` (every k is in the future of every q — the
  causal mask already drops these in the v0 path).
- **Full overlap (run kernel as v0)**: `0 ≤ min_gap` *and*
  `max_gap ≤ w` (every (q, k) pair satisfies the window).
- **Boundary**: otherwise. The window edge crosses through the
  chunk pair. Apply a per-row mask: row `i` (0-indexed within the
  Q chunk) keeps K-positions with absolute-gap-in-window
  `q_pos - k_pos ∈ [0, w]`, i.e. local K indices `j` satisfying
  `(g_k · c + j) ∈ [g_q · c + i - w, g_q · c + i]`. Translated to
  local-K index range: `j ∈ [(g_q - g_k) · c + i - w, (g_q - g_k) · c + i]`,
  clamped to `[0, c)`. Apply the v0 kernel call with the v0 mask
  first; then zero (or NaN-guard) the cells that fall outside the
  per-row local-K range. Reduction stays plain-sum in fp32 per
  SPEC §2.

The (rank, step) tile is built from chunk-pair sub-tiles per the v0
classification:

- `step == 0` (diag): Q chunks `{r, 2·cp-1-r}` × K chunks
  `{r, 2·cp-1-r}`. Four sub-tiles. Diagonal sub-tiles `(g, g)`
  use `min_gap = -(c-1)`, `max_gap = c-1` — full-overlap when
  `w ≥ c-1`; boundary when `0 < w < c-1`. Off-diagonal sub-tile
  `(2·cp-1-r, r)` has `min_gap = (2·cp-1-2r-1)·c + 1` — far past;
  skip when `min_gap > w` (most cp_size > 2 cases).
- `step ∈ [1, r]` (lower-tri): K = peer's first-half chunk
  `g_k = r - step`. Q chunks `{r, 2·cp-1-r}` × this K. Two sub-tiles
  with `(g_q - g_k) ∈ {step, 2·cp-1-2r+step}` — apply the
  classification per sub-tile.
- `step ∈ (r, cp-1]` (upper-tri): K = peer's second-half chunk
  `g_k = 2·cp-1-(r-step)`. Only Q-second-half (chunk `2·cp-1-r`)
  participates (v0 already drops Q-first-half here because the K
  chunk is fully in Q-first-half's future). One sub-tile with
  `(g_q - g_k) = step - r`.

Each chunk-pair classification is constant-time (compare two
ints to `w` and `0`); no per-token work for skip/full-overlap
sub-tiles. Boundary sub-tiles need a per-row mask vector of length
`c` (or `O(c)` work per row), applied via a single fp32 multiply
on the partial output before accumulation.

## 3. Public API impact

`hstu_attn_varlen_cp_func`: **same signature as v0**. The window
argument that v0 hard-rejects (`window_size != (-1, 0)`) is allowed
through the dispatcher; the wrapper translates it into the per-tile
classification at the top of `_multi_gpu_forward`.

The 13-item hard-guard list in `_enforce_v0_contract` loses the
`window_size != (-1, 0)` check; that guard moves into a new
`_enforce_v0_5_contract` that still rejects `(w_left, w_right)` with
`w_right > 0` (only sliding-causal, not full sliding window).

## 4. Test plan

Extend `examples/hstu/test/cp/conftest.py::REFERENCE_MATRIX` with
`window_size` cases:
  - `cp2_w64`: cp=2, sample length 256, `w=64`
  - `cp4_w256_eq`: cp=4, equal-length 1024, `w=256`
  - `cp8_w_overlap_boundary`: cp=8, sample length 512, `w=64` (window
    size that triggers boundary tiles)
  - `cp4_w_full_local`: cp=4, sample length 64, `w=L` (sanity:
    sliding-causal with `w >= L` is equivalent to pure causal)

Each case compares against the same single-GPU baseline call with
the same `window_size`. Tolerances unchanged (bf16 fwd 2e-2, bwd 5e-2).

---

## 5. Out of scope for v0.5

- **Sliding window with `w_right > 0`** (lookahead): rare in HSTU
  workloads; defer to v0.6.
- **Per-sample `w`**: the kernel takes a single `window_size` for the
  whole batch. v0.5 inherits this constraint.
