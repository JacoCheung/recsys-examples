This document is the design spec for the v0 HSTU context-parallel implementation. Every claim cites a line number in the live source files listed under each section. The matching, interactive walkthrough of the worked example is shipped as HSTU_CP_WALKTHROUGH.html.

The autograd boundary (_HSTUVarlenCPFunc) is what keeps the entire ring transparent to the rest of the trainer: forward saves the local Q/K/V plus the cu_seqlens (hstu_attn_cp.py:2005), and .backward() re-runs the ring in reverse using those saved tensors.

The backward path mirrors forward. The reverse ring runs after the local backward kernels so each rank's dK/dV partials get sent back to the peer that owned the K/V originally, then accumulated.

Why the backward re-rotates KV in the same (forward) direction, then sends dKV in the reverse direction at the end: at backward step s the rank holds peer (rank - s) % cp_size's K/V (reconstructed by re-running the same ring), so the kernel produces dK/dV for that peer's K/V (hstu_attn_cp.py:1739-1745). The dKV reverse-ring then routes those partials home — send_dst = (rank - step) % cp_size (hstu_attn_cp.py:1854) which is exactly that peer.

§2. DualChunkSwap layout

A global sample of length L (L % (2*cp_size) == 0 is enforced at dispatch — hstu_attn_cp.py:389-391) is split into 2 * cp_size chunks of size c = L / (2*cp_size). Rank r owns chunks {r, 2*cp_size - 1 - r} (hstu_attn_cp.py:379, hstu_attn_cp.py:535). Per-rank local layout per sample is [chunk_r ; chunk_(2*cp_size - 1 - r)] (hstu_attn_cp.py:396-401).

Why paired chunks (and not naive contiguous halves)

A naive layout would give rank r the contiguous range [r * L/cp_size, (r+1) * L/cp_size). Under causal masking that loses load balance hard: rank 0 gets the first quarter (very few K accesses per Q row — every Q row only sees its short prefix), rank 3 gets the last quarter (each Q row sees the full prefix, so kernel work is ~L² per row). The total work then differs by ~(cp_size)× between rank 0 and rank cp_size-1.

The paired layout {r, 2*cp_size - 1 - r} cancels that imbalance: rank 0 takes chunk 0 (cheapest under causal — Q rows only see K rows [0, q+1) ≤ [0, c)) plus chunk 2*cp_size-1 (most expensive — Q rows see almost the entire K). Rank cp_size/2 - 1 takes chunk cp_size/2 - 1 (medium) plus chunk cp_size/2 (medium). Each rank's total K-access count is the same.

Concretely for cp_size = 4, c = L/8:

  • Rank 0: chunk 0 (Q rows see ≤ c K rows) + chunk 7 (Q rows see ~8c K rows). Work proxy ≈ c² + 8c² = 9c².
  • Rank 1: chunk 1 (Q rows see ≤ 2c) + chunk 6 (Q rows see ~7c). Work proxy ≈ 2c² + 7c² = 9c².
  • Rank 2: chunk 2 + chunk 5 → 3c² + 6c² = 9c².
  • Rank 3: chunk 3 + chunk 4 → 4c² + 5c² = 9c².

All ranks see ≈ 9c² work — flat. This is the load-balancing argument that makes r ↔ 2*cp_size-1-r the right pairing (the same trick Megatron-Core CP uses for its "stripe" layout, ported here at chunk granularity rather than token granularity).

The dispatch (get_batch_on_this_cp_rank_for_hstu, hstu_attn_cp.py:337) just permutes rows; no torch.distributed calls (hstu_attn_cp.py:331). The inverse for tests is gather_global_from_cp_rank (hstu_attn_cp.py:414); production uses gather_jagged_from_cp_rank with an all-reduce SUM (hstu_attn_cp.py:591, summing zeros-elsewhere shards reproduces the global tensor — hstu_attn_cp.py:603-605).

§3. Ring P2P communication

Each rank exchanges its current K/V tile with its neighbour for cp_size - 1 ring steps so that, by the end, every rank has touched every peer's K/V exactly once.

Forward direction (_ring_send_recv_kv, hstu_attn_cp.py:911-979):

  • dst = (rank + 1) % cp_size (hstu_attn_cp.py:945)
  • src = (rank - 1) % cp_size (hstu_attn_cp.py:946)

Backward direction is the same _ring_send_recv_kv helper called with direction="backward" (hstu_attn_cp.py:947-949), which flips the neighbour pair. The forward path of the multi-GPU forward and of the KV-reload portion of the backward use direction="forward" (hstu_attn_cp.py:1573, hstu_attn_cp.py:1784). Only the dKV exchange at the end of _multi_gpu_backward_arbitrary is sent in the reverse direction (hstu_attn_cp.py:1854 — send_dst = (cp_rank - step) % cp_size).

Why no P2P in the last step: at step cp_size - 1 each rank already holds the last peer's KV; no further rotation is needed. The code guards this explicitly with if step < cp_size - 1 around the _ring_send_recv_kv call (hstu_attn_cp.py:1205).

The backward reverse-ring (post-loop dKV exchange, hstu_attn_cp.py:1853-1879) runs exactly once per non-zero step, i.e. cp_size - 1 exchanges. Each iteration sends dk_p/dv_p to (rank - step) % cp_size and receives from (rank + step) % cp_size. Note this isn't a single direction — at step 1 vs step 3 the same rank sends to different peers. It's not a "ring" in the rotating sense; it's cp_size - 1 independent SendRecv pairs (one per forward step where this rank computed grads for somebody else's KV).

NCCL invariant: two-pair batches, not one four-pair batch

The kernel issues K and V as two separate 2-op batches, not a single 4-op batch (hstu_attn_cp.py:961-973). The block comment at hstu_attn_cp.py:957-960 records the rationale: bundling all four ops into one batch_isend_irecv call hangs in some NCCL/torch combinations on the production image's NCCL on A100 PCIe. Two 2-op batches is the verified-stable shape.

§4. Comm/compute overlap (Gantt)

Two CUDA streams: the default stream (kernel + accumulator) and a secondary comm_stream allocated lazily per device (_get_cp_stream, hstu_attn_cp.py:307-324). The pattern in _multi_gpu_forward_arbitrary (hstu_attn_cp.py:1202-1277) is:

  1. comm_stream.wait_stream(default_stream) — the comm stream waits for the previous kernel's read of the recv buffer (so NCCL doesn't write into a buffer that the kernel is still reading) (hstu_attn_cp.py:1206).
  2. _ring_send_recv_kv(..., comm_stream=comm_stream) — NCCL issued on comm_stream (hstu_attn_cp.py:1207).
  3. The kernel for this step (operating on cur_k/cur_v — the KV we already had) runs on the default stream (hstu_attn_cp.py:1241).
  4. for r in reqs: r.wait() — CPU-blocking; ensures the NCCL Work handles are drained (hstu_attn_cp.py:1273).
  5. default_stream.wait_stream(comm_stream) — the default stream waits for the comm stream so the next-step kernel sees the recv'd bytes (hstu_attn_cp.py:1275).
  6. Pointer swap of cur_k ↔ recv_k, cur_v ↔ recv_v (hstu_attn_cp.py:1276-1277).

What this diagram makes obvious:

  • Overlap succeeds when kernel ≥ NCCL (the kernel step i bar fully covers the NCCL P2P bar for step i+1's KV). For typical HSTU shapes the attention kernel runs tens of milliseconds and one P2P of ~56 MB runs single-digit milliseconds on NVLink — overlap is real.
  • Overlap stalls when kernel < NCCL or on the last step. The last step has no further P2P, so the trailing to(dtype) after the loop is straight on the default stream.
  • The CPU-blocking Work.wait() lives on neither stream — it is a synchronous barrier that pauses Python until the NCCL handle is drained (hstu_attn_cp.py:1273-1274). The actual GPU-side ordering is enforced by the wait_stream calls.

The same pattern appears in _multi_gpu_backward_arbitrary (hstu_attn_cp.py:1771-1844) for the KV-reload portion of backward. The dKV reverse-ring at the end uses a slightly relaxed pattern: K and V issuance proceed concurrently inside NCCL without a wait between them, then a single wait at the end (hstu_attn_cp.py:1862-1879).

The clone is mandatory

cur_k = k_local.clone() (hstu_attn_cp.py:1185) cannot be replaced with cur_k = k_local — NCCL's batch_isend_irecv validator rejects the bare reference with ValueError: Tensors for P2P must be non-overlapping and dense (block comment, hstu_attn_cp.py:1180-1184). The clone also prevents a subtler bug: without it, the post-step buffer swap at hstu_attn_cp.py:1276 would rebind cur_k = recv_k but the next step's NCCL would write into the original k_local storage — silent data corruption (block comment in the legacy path, hstu_attn_cp.py:1030-1033).

§5. Arbitrary-mask func tensor

The HSTU FBGEMM kernel exposes an "arbitrary mask" interface where each Q row's allowed K positions are encoded as disjoint integer intervals packed into a fixed-width func tensor. Layout (_mask_func.py:19-30, _mask_func.py:213-250): 

func.shape = (1, NFUNC, total_local_q)   # int32

slot 0  : MaxFunc[0]    upper of interval 0  (lower implicit = 0)
slot 1  : MinFunc[0]    lower of interval 1
slot 2  : MaxFunc[1]    upper of interval 1
slot 3  : MinFunc[1]    lower of interval 2  (NFUNC ≥ 5 only)
…

NFUNC must be odd (_mask_func.py:344); NFUNC = 3 supports up to 2 disjoint intervals per row (_mask_func.py:482). The HSTU CP wrapper hardcodes NFUNC = 3 (hstu_attn_cp.py:1235), enough for history-causal + target-group-band — the standard production family.

Note the trailing axis is total_local_q (jagged, sum of per-sample seqlens), not max_seqlen_q. The kernel reads func_ptr + binfo.sum_s_q + (j * func_ids_stride) + q_local, which only resolves correctly with the jagged trailing axis (block comment, _mask_func.py:540-547).

Why func is more flexible than is_causal

Flash-attn (and most fused attentions) take a boolean is_causal plus optional (window_left, window_right) for sliding — that's a single regular structure built into the kernel. HSTU's func tensor is a per-row arbitrary integer interval list: each Q row independently declares which K positions contribute. That covers:

  • pure causal: row q's slot[0] = q+1, no other slots used;
  • contextual prefix: rows [0, nc) see all of [0, history_end), rows [nc, history_end) see [0, q+1) (_mask_func.py:79-89);
  • target-group: rows in the target region see history and a per-group-aligned target band (_mask_func.py:91-111);
  • sliding-causal: each row's lower bound becomes max(0, q - w_left) (_mask_func.py:77);
  • arbitrary CP-step mask: rows see only the K positions that landed on the current peer's chunks (the whole reason this module exists).

The structured-mask layer of the kernel runs first, then the kernel intersects its result with func (block comment, hstu_attn_cp.py:1252-1255). To avoid double-application the CP path disables the structured layer (window_size=(-1,-1), num_contexts=None, num_targets=None, target_group_size=1) when calling the kernel and pushes the entire mask into func (hstu_attn_cp.py:1252-1255).

Per-step localisation: localize_func_for_cp_step

At ring step s rank r holds K/V from peer (r - s) % cp_size (_mask_func.py:326-328, hstu_attn_cp.py:1226-1240). The local K layout is therefore [chunk_peer ; chunk_(2*cp - 1 - peer)] per sample (_mask_func.py:328). The localizer's job: for each Q row the rank owns, take the global causal/target/contextual interval list and project it onto the local K layout.

The hot-path implementation is numpy-vectorised (_mask_func.py:116-210, _mask_func.py:393-518), running on CPU and copying the resulting array to device once per call — block comment _mask_func.py:383-391 records that per-element CUDA writes in a Python loop produced ~277× slowdown vs the structured path before the vectorisation. The CPU build + bulk H2D copy is two orders of magnitude faster.

Concrete example: cp_size=4, L=16, c=2, cp_rank=0, step=0

Sample 0 of length 16, c = L / (2*cp_size) = 2. Rank 0 owns Q chunks {0, 7}, so local Q maps to global Q rows [0, 1, 14, 15]. At step 0, peer = rank 0 — K layout is [chunk_0 ; chunk_7] = global K rows [0, 1] ∪ [14, 15] (local positions [0, 1, 2, 3]).

Causal-only (no contextual, no targets), so each Q row's allowed K is [0, q+1).

local_qglobal_qglobal K intervallocal K intervalNFUNC=3 slots

The merge step is in _mask_func.py:498-510: chunk_first contributions land in local [0, c), chunk_second in [c, 2c), so when adjacent they are merged into a single interval and slot[0] alone suffices. Sample length 16 with cp_size=4 yields 4 local Q rows for sample 0; the full func tensor for two-sample batch (sample 1 of length 32) has trailing axis 12 (4 + 8).

§6. Caching and pooling

Two module-level data structures back the steady-state perf path. Both are documented at the call site and both have regression tests in examples/hstu/test/cp/.

6.1 _cp_func_cache

_cp_func_cache: dict[tuple, torch.Tensor] — module-level (NOT thread-local) at hstu_attn_cp.py:183.

Key: full content tuple (step, cp_size, cp_rank, cu_seqlens.tolist(), num_contexts.tolist(), num_targets.tolist(), target_group_size, window_size, NFUNC) (hstu_attn_cp.py:271-281).

Why module-level, not TLS: PyTorch autograd backward runs on a worker thread, not the forward thread. A threading.local() cache populated on the forward thread is invisible from the worker. That was the cw-dfw round-4 regression — ~734 ms/step instead of ~70 ms because backward rebuilt every layer's func tensor from scratch (block comment, hstu_attn_cp.py:160-174). Pinned by test_func_cache.py:test_cache_visible_from_other_thread (test_func_cache.py:97-132): the test populates from the main thread and asserts the worker thread retrieves the same tensor object.

Why content-keyed, not identifier-keyed: the HSTU benchmark cycles num_generated_batches (~100) unique cu_seqlens values across training steps. Identifier-only keying would silently return a stale func for a different batch's mask shape — wrong mask = wrong grads = silent training corruption. Pinned by test_func_cache.py:test_cache_keys_on_cu_seqlens_content (test_func_cache.py:135-176): two distinct cu_seqlens values must produce distinct cache entries.

Caller fast-path: callers that already know cu_seqlens.tolist() (the autograd Function entry computes it once per training step, hstu_attn_cp.py:1974) pass it through cu_seqlens_global_tuple to skip the internal hash sync (hstu_attn_cp.py:256-260, test_func_cache.py:179-237).

Memory bound: _CP_FUNC_CACHE_MAX = 1024 (hstu_attn_cp.py:184); FIFO eviction when exceeded (hstu_attn_cp.py:289-290). Pinned by test_cache_caps_growth (test_func_cache.py:240-271).

Scope hooks: cp_func_cache_scope_enter() (hstu_attn_cp.py:187-197) clears the dict; cp_func_cache_scope_exit() (hstu_attn_cp.py:200-202) is a no-op kept for symmetry. The hot path never calls scope_enter from inside HSTUBlock.forward (hstu_block.py:173-181) — that would wipe the cross-step cache and re-introduce the round-5/6 hit rate ceiling. Pinned by test_scope_exit_keeps_cache_alive_for_backward (test_func_cache.py:274-293).

6.2 _recv_buffer_pool

_recv_buffer_pool: dict[tuple, torch.Tensor] — module-level at hstu_attn_cp.py:107. Returned via _get_recv_buffer (hstu_attn_cp.py:110-130).

Key: (template.dtype, template.device, slot) — NOT shape (hstu_attn_cp.py:121). slot is a logical name like "fwd_recv_k", "fwd_recv_v", "bwd_recv_k", "bwd_recv_v", "bwd_recv_dk", "bwd_recv_dv" (hstu_attn_cp.py:1187-1188, hstu_attn_cp.py:1752-1753, hstu_attn_cp.py:1851-1852, test_recv_buffer_pool.py:130-137).

Storage layout: 1-D contiguous, template.numel() elements allocated on first use (hstu_attn_cp.py:124-126); grown in-place if a later call needs more elements (same line). Returned as narrow(0, 0, n).view(template.shape) (hstu_attn_cp.py:130), which stays contiguous because the underlying storage is contiguous and narrow is a front-slice. NCCL P2P consumes it natively (block comment, hstu_attn_cp.py:127-130).

Why not key by shape: round-10 lesson, recorded at hstu_attn_cp.py:91-97: a shape-keyed pool produces a fresh entry for every distinct total_tokens the dataset emits. The HSTU benchmark cycles 100 unique cu_seqlens × 6 slots = 600 entries × ~56 MB each = ~33 GB — OOM at iter ~400 with CUDA error: an illegal memory access. Pinned by:

  • test_different_shapes_same_slot_share_storage_when_fits (test_recv_buffer_pool.py:73-100): two different-shape templates in the same slot share storage when the smaller fits.
  • test_growing_shape_grows_storage_in_place (test_recv_buffer_pool.py:103-120): a larger shape grows the entry, doesn't add a new one.
  • test_pool_bounded_under_simulated_jagged_workload (test_recv_buffer_pool.py:123-146): 100 distinct shapes × 6 slots yields 6 entries, not 600.

Stream correctness: each ring step ends with default_stream.wait_stream(comm_stream) followed by reading the buffer; the next layer's comm_stream.wait_stream(default_stream) before its NCCL P2P guarantees the previous read has completed before NCCL writes (block comment, hstu_attn_cp.py:99-105). Reusing storage across the 8 layers' forwards is therefore safe.

Distinct slot per logical recv tensor: recv_k and recv_v are read concurrently within a single ring step, so they MUST be distinct physical storages. Pinned by test_distinct_slots_map_to_distinct_storage (test_recv_buffer_pool.py:59-70). Likewise the bwd KV-reload uses different slots (bwd_recv_k, bwd_recv_v) from the bwd dKV exchange (bwd_recv_dk, bwd_recv_dv) so they don't collide mid-step (hstu_attn_cp.py:1849-1852).

The empty_like + first-iteration copy_ pattern (vs zeros_like + +=) skips the ~112 MB memset per accumulator, saving ~50 µs per accumulator × 8 layers ≈ 0.4 ms / training step on the forward side and ~1.2 ms / training step across the 3 backward accumulators (block comment, hstu_attn_cp.py:1190-1199, hstu_attn_cp.py:1755-1764).

7.5 Final gather

Each rank's local 12-row output (after dtype cast back from fp32, hstu_attn_cp.py:1279) is scattered into a (48, num_heads, head_dim) zeros buffer via local_to_global and SUM-all-reduced: gather_jagged_from_cp_rank at hstu_attn_cp.py:591-622. Each global row is owned by exactly one rank, so SUM is identity (hstu_attn_cp.py:603-605). Test uses the same pattern at test_cp_forward.py:159-165.

§8. Out-of-scope (v0)

Hard rejections live in _enforce_v0_contract (hstu_attn_cp.py:629-753). The list:

  • Megatron-Core striped CP layout. v0 uses DualChunkSwap. Striped CP is not implemented; no entry point exists in _HSTUVarlenCPFunc.forward.
  • Ulysses sequence parallel. cp_comm_type only accepts "p2p"; anything else raises (hstu_attn_cp.py:2208-2211, hstu_attn_cp.py:1945-1948). Ulysses would correspond to cp_comm_type="a2a"; not wired.
  • CP + sequence_parallel composition. Rejected at the block level (hstu_block.py:66-72) because the SP preprocessor scatters jd.values along the row dim while CP dispatch indexes with global offsets — shape/index mismatch.
  • FP8 quantisation. quant_mode != -1 rejected at hstu_attn_cp.py:711-714. The CP reduction is in fp32 by SPEC §2, which the FP8 quant path would conflict with.
  • kv_cache / paging. Rejected at hstu_attn_cp.py:700-707 — kv_cache, page_offsets, page_ids, last_page_lens all must be None.
  • rab / has_drab. Rejected at hstu_attn_cp.py:695-698.
  • seqused_q / seqused_k. Rejected at hstu_attn_cp.py:716-719 — the wrapper does not pass them through to the kernel for cp_size > 1.
  • Sliding-causal under CP with num_contexts or num_targets. Mirrors the FBGEMM kernel ABI invariant: contextual / target masks require window_size = (-1, 0) (hstu_attn_cp.py:670-684). At cp_size > 1 the wrapper enforces the same — keeps behaviour identical to cp_size == 1 (which is rejected by the kernel itself).
  • Explicit func tensor under CP. The CP-step localisation requires the analytical predicate, not an opaque tensor. func is not None rejected at hstu_attn_cp.py:686-693.
  • max_seqlen_q != max_seqlen_k. Rejected at hstu_attn_cp.py:2159-2163 — HSTU is self-attention only.
  • HSTU layer types other than NATIVE under CP. Rejected at hstu_block.py:60-65 — CP plumbing is wired only through the NATIVE layer.
  • Heterogeneous mask under CP backward. Forward is supported via the func path (_multi_gpu_forward_arbitrary). Backward under het-mask is the same code path (_multi_gpu_backward_arbitrary); the broader het-mask track details are in het_mask_design.md.
  • apply_dualchunkswap_to_jagged with padding_length > 0. Rejected at hstu_attn_cp.py:521-526 — SP+CP composition out of v0 scope.
